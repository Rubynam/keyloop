Unified Service Scheduler

Booking a service bay and a qualified technician for a car — fast for readers, and impossible to double-book.

~20s. Introduce the problem in one sentence: a dealership scheduler where a booking needs a free bay AND a qualified, free technician for the whole service duration.
The problem

A booking needs two scarce resources at once

Business rule
  • One service bay that accepts the vehicle type
  • One technician who is certified for the type and skilled for the service
  • Both free for the whole duration (oil change 60 min, major service 180 min)
  • A car cannot be in two places at once
Non-functional
  • Correctness first: zero double bookings, even under concurrent requests
  • Read-heavy: customers refresh availability many times before they book
  • Horizontally scalable, stateless API
  • Every request traceable end to end

Core tension: availability reads want a cache; booking writes need a single source of truth.

~40s. Stress the tension in the callout — every later design choice comes from it.

Architecture

Container view

~50s. Walk left to right: nginx → two stateless API replicas → Postgres (truth) and Redis (cache). The batch app relays outbox events into cache invalidation. Everything exports spans to Jaeger.
Components

Who does what

ComponentRole
nginxSingle entry point, round-robin to API replicas via Docker DNS, adds X-Request-Id, drops client traceparent.
server-apiStateless REST service: validates input, computes availability, books appointments. Owns the schema (Flyway).
scheduler-batchOutbox relay (FOR UPDATE SKIP LOCKED, 3 retries → FAILED) and daily cleanup job. ShedLock = one run per tick across replicas.
PostgreSQLSingle source of truth. Exclusion constraints make double booking impossible. Also the outbox queue.
RedisRead-side cache for availability, versioned keys + stampede lock. Fail-open: if down, read Postgres.
JaegerDistributed tracing, OTLP straight from the apps. Logs stay JSON on stdout with the traceId.

Data flow

Three flows, one rule: the cache never decides

① Read · cache-aside

GET /availability
→ ver = GET avail:ver:{dealer}:{date}
→ GET avail:…:v{ver}:…
  hit → 200
  miss → lock (SET NX PX)
  → Postgres → compute slots
  → SET with TTL + jitter

② Write · booking

POST /appointments
→ validate (404 / 400 / 422)
→ candidates from Postgres
→ BEGIN
  INSERT appointment
  INSERT outbox_event
  COMMIT → 201

③ Invalidate · outbox

relay every 500 ms
→ SELECT … FOR UPDATE
  SKIP LOCKED
→ INCR avail:ver:{dealer}:{date}
→ mark PROCESSED
  (fail ×3 → FAILED)

Why it is safe: a stale cache can only show a slot as free when it is not. The booking still hits the DB constraint → 409. Stale reads cost UX, never correctness.

~60s. Key insight: bumping a version key instead of deleting keys means we never need to know which cache keys exist. Old versions just expire by TTL.
Technology choices

Why this stack

PostgreSQL 18

EXCLUDE USING gist on time ranges enforces "no overlap" atomically — no app-level locks. Native uuidv7() for time-ordered ids.

Redis 8

Sub-ms reads for the hot availability path; SET NX PX + Lua for stampede protection; easy versioned keys.

Spring Boot 4.1 · Java 25

Mature MVC + Bean Validation + ProblemDetail; Micrometer Observation gives HTTP/JDBC/Redis spans with no code.

Transactional outbox

Booking + event commit together, so cache invalidation is never lost — without a message broker to run.

Spring Batch + ShedLock

Cleanup job with restartable metadata; ShedLock makes scheduled jobs safe with many replicas.

Testcontainers · ArchUnit · JaCoCo · Locust

Real Postgres/Redis in tests, architecture rules as tests, coverage per module, load + race tests from JSON scenarios.

~50s. Pick two to talk about: EXCLUDE constraint and outbox. Mention we chose NOT to add Kafka — polling 500ms is enough at this scale.
Observability strategy

Logs, traces, and (next) metrics

Logging · done
  • Structured lines on stdout
  • [correlationId] [traceId,spanId] on every line
  • 4xx → WARN, 5xx → ERROR
  • No customer data in logs
Tracing · done
  • OTLP → Jaeger, sampling configurable
  • One trace per request: HTTP → SQL → Redis
  • Batch: job → step → SQL
  • Noise filtered (actuator, relay ticks)
Metrics · next
  • Prometheus + Grafana
  • OTel Collector to fan out
  • Booking 409 rate, cache hit ratio, outbox lag

Every error body carries "traceId" → paste it into Jaeger → see exactly which SQL / Redis call failed.

~40s. Be honest: metrics are deferred on purpose; tracing gave the most value per hour of work.

How the backend works

Life of a booking request

nginx→ RequestIdFilter→ AppointmentController
@Valid→ AppointmentServiceImpl→ Repositories (JDBC)→ PostgreSQL 
// AppointmentServiceImpl.book — checks in a fixed order, cheapest first
0. Idempotency-Key seen?        → replay same appointment   (Idempotent-Replayed: true)
1. ids exist?                   → 404
2. vehicle belongs to customer? → 400
3. on slot grid, inside hours?  → 422
4. vehicle already busy?        → 422
5. candidate (bay, technician) pairs from Postgres → none: 409
6. for each pair: BEGIN · INSERT appointment · INSERT outbox · COMMIT → 201 + Location
~50s. Point out idempotency: the client can safely retry a POST on timeout.
MVC pattern

Layers talk only through interfaces

Controller ──► XxxService (interface)
                   └─► XxxServiceImpl
                          │
                          ▼
              XxxRepository (interface)
                   └─► JdbcXxxRepository  ← SQL only here

package layout: layer first, then feature
controller/appointment/
service/appointment/impl/
repository/appointment/impl/
cache/availability/impl/      Redis port
tracing/<feature>/impl/      span port
  • Controller: one call to the service, returns a DTO record — never a row type
  • Service: business rules, depends only on repository/cache interfaces
  • Repository: JdbcClient + SQL, translates DB errors to domain exceptions
  • Constructor injection only; no magic strings (ApiPaths, HeaderNames)

ArchitectureTest (ArchUnit, ARC-01…10) turns these rules into failing tests — so they survive refactors and AI-written code.

The challenge

Two customers book the same slot at the same millisecond

-- V2__domain_schema.sql  (btree_gist)
CONSTRAINT ex_appointments_technician
  EXCLUDE USING gist (
    technician_id WITH =,
    tstzrange(start_time, end_time, '[)') WITH &&
  ) WHERE (status <> 'CANCELLED'),
-- same for service_bay_id and vehicle_id
  • Postgres decides, atomically, across every replica
  • '[)' half-open: 09:00–10:00 and 10:00–11:00 do not clash
  • One short transaction per pair: technician taken → next pair; bay taken → stop; vehicle taken → 422
  • No SELECT … FOR UPDATE, no distributed lock, no Redis in the decision
~70s — the most important slide. Explain why app-level locks or Redis locks are not enough (lock expiry, multiple replicas), and why the DB constraint is the only place where the check and the insert are one atomic step.

Observability in code

One aspect, one id, one trace

// common-logging · MethodLoggingAspect
@Around("@within(RestController)
      || @within(Service)
      || @annotation(Scheduled)")
Object logCall(ProceedingJoinPoint jp) {
  // HTTP: id from RequestIdFilter; jobs: new id
  ...
  log.info("[{}][{}][{}][{}][{}]",
     service, method, correlationId, input, output);
  // ClientError (4xx) → WARN, else ERROR
}
  • RequestIdFilter puts X-Request-Id into MDC → every log line of the request shares it
  • Booking loop logs one line per try: try 2/3 pair=… outcome=TECHNICIAN_TAKEN — no customer data
  • Business spans go through a tracing/<feature> port; Micrometer types stay out of services
  • Noise filters drop actuator + 500 ms relay ticks from Jaeger

Load-test reports parse these logs: WARN/ERROR by exception, log lines per request — observability feeds back into tuning.

Summary

Key takeaways

✔ Correct by construction

Double booking is blocked by Postgres exclusion constraints, not by app code or Redis.

✔ Fast reads, safe staleness

Versioned cache-aside + outbox invalidation. Stale cache → 409, never a wrong booking.

✔ Clean, enforced layering

MVC through interfaces, REST rules and constants — enforced by ArchUnit.

✔ Observable & tested

traceId in every log and error body; Testcontainers + Locust race tests with 0 violations.
